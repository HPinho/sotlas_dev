# Sotlas v1.0 — Architecture Audit, Universal Systems Strategy & Roadmap

> **Design Axiom:**  
> Sotlas is a single, coherent systems language spanning the entire computing spectrum — from zero-runtime baremetal kernels and hard real-time game engines to high-level desktop/mobile applications and AI tensor pipelines — without compromising safety, ergonomics, or determinism.

---

## 1. Executive Summary & Current State Audit

Sotlas has already achieved what few language projects ever reach: a working SSA intermediate representation (SIR), an end-to-end AST-to-C11 native pipeline, freestanding prelude support, and an initial self-hosted compiler binary (`sotlas_native.exe`). 

However, transitioning from an ambitious research compiler to an industrial-grade **Tier-1 systems language** capable of challenging C, C++, Swift, Rust, and Zig requires two transformations:
1. **Closing Language & Runtime Completeness:** Moving from stubbed grammar productions to fully lowered, zero-overhead primitives (closures, monomorphized generics, specs, `defer`, and owned string slices).
2. **Purging "AI-Slop" and Prototyping Artifacts:** Removing verbose tutorial comments, auto-generated banners, and fragmented Portuguese/English branding. The codebase and compiler must look and feel like an elite, battle-tested systems engineering effort.

## 2. Resolving the Open Questions (Architectural Decisions)

Before expanding the roadmap, the three fundamental open questions from the initial audit must be resolved with absolute technical conviction:

### Decision 1: Comment Language & Codebase Demographics
* **Verdict: 100% English for all compiler internals, runtime headers, and standard library source files.**
* **Rationale:** Every major systems programming toolchain that attained global adoption (Linux, LLVM, Swift, Rust, FreeBSD, Zig) standardizes strictly on English for source code, identifiers, commit messages, and internal compiler diagnostics.
* **Documentation Policy:** Official user guides, "The Sotlas Book", and tutorials will be published bilingually (English & Portuguese). Internal architecture docs and code comments remain exclusively English.

### Decision 2: Implementation Sequencing
* **Verdict: Concurrently execute Phase A (Fingerprint Cleanup) and Phase B (Core Usability Primitives).**
* **Rationale:** A compiler cannot be presented to the world with tutorial comments or "Generated by AI" headers. Simultaneously, developers cannot test real systems without `defer`, an owned `String`, and iterator lowering. They must be resolved in parallel immediately.

### Decision 3: Depth of Generics (Surface Syntax TBD)
* **Verdict: Full compile-time monomorphization by default; explicit dynamic dispatch via Spec Objects (`*dyn Spec`).**
* **Rationale:** 
  - For **kernel, baremetal, and game engines**, monomorphization yields zero runtime overhead, enables inlining, and exposes memory layouts for SIMD vectorization.
  - To prevent binary bloat in freestanding kernels, the SIR Dead-Code Elimination (DCE) pass strips uncalled monomorphized instances before code generation.
  - When dynamic heterogeneity is explicitly required (e.g., heterogeneous UI widget hierarchies), Sotlas uses fat pointers (`data_ptr` + `vtable_ptr`) via `*dyn Spec`.

### Decision 4: Backend Architecture — Portable Bootstrap + Native Codegen
* **Verdict: C11 remains a bootstrap/reference backend; it is not the permanent execution model of Sotlas.**
* **Canonical pipeline:** `Source -> Typed AST -> SIR -> target lowering -> backend`. SIR is the stable boundary between language semantics and target-specific code generation.
* **Native backend direction:** Sotlas will grow a first-party native backend that emits relocatable object code / machine code for supported targets. Textual assembly is an inspection/debug product (`--emit=asm`), not the primary compiler transport format.
* **Why not ASM-only:** emitting textual assembly directly as the sole backend would force instruction selection, register allocation, ABI lowering, relocations, object formats, debug information, unwind metadata, and target-specific optimization to become mandatory before the language core is stable.
* **Why keep C11:** the C11 backend provides a portable bootstrap path, a readable semantic reference, cross-target bring-up, differential testing, and a fallback for new architectures while the native backend matures.
* **Baremetal rule:** `target barecore` must not rely on hosted C runtime semantics. Once the native backend is available for a target, kernels, bootloaders, interrupt paths, MMIO, and architecture intrinsics should prefer direct native lowering.
* **Hosted rule:** desktop, server, game-engine, and AI/HPC builds may select the best available backend per target (native backend or LLVM), without changing Sotlas source semantics.
* **Backend parity requirement:** a feature is not `SUPPORTED` merely because one backend accepts it. Semantics must be defined at Typed AST/SIR level and each claimed production backend must either implement them or reject them explicitly.

### Long-Term Native Identity: Sotlas as a Modern Machine Layer

Sotlas is intended to grow beyond using C as an implementation transport. The long-term objective is for Sotlas to become a **modern, typed machine-facing language layer**: occupying a role analogous to assembly for direct machine control, while preserving the language's higher-level guarantees.

This does **not** mean replacing Sotlas syntax with textual assembly. It means the compiler must eventually be capable of lowering Sotlas semantics directly into target instructions and object code without requiring generated C as an intermediate source language.

The native path should preserve:

- explicit register- and ABI-aware lowering where required by `barecore`, `trapfn`, MMIO, SIMD, atomics, context switching, and hardware control;
- typed values, layouts, ownership/resource obligations, effects, privilege boundaries, and deterministic cleanup before target instruction selection;
- direct access to machine-specific capabilities through audited Sotlas constructs rather than opaque C compiler extensions;
- target-specific optimization after SIR while keeping source-level semantics target-independent;
- optional textual assembly output for inspection, diagnostics, teaching, performance analysis, and low-level auditing.

Conceptually:

```text
Traditional assembly:
source text -> assembler -> machine/object code

Long-term Sotlas native path:
Sotlas -> Typed AST / Sema -> SIR -> target lowering -> machine/object code
                                      |
                                      +-> optional assembly listing
```

In that sense, Sotlas should eventually be able to serve as a **modern successor layer to assembly for systems work**: close enough to the machine for kernels, bootloaders, drivers, engines, SIMD/HPC, and runtime internals, while remaining expressive enough for hosted applications, professional software, games, and AI systems.

C11 remains valuable as a bootstrap/reference backend and portability oracle, but it must never become a semantic dependency of the language. The canonical semantics live above every backend, in Typed AST/SIR and the target contracts.

The intended long-term backend matrix is:

```text
Sotlas source
    |
    v
Typed AST / Sema
    |
    v
SIR
    |
    +--> C11 backend ---------> C compiler ---------> object/binary
    |      bootstrap/reference
    |
    +--> Native backend ------> .o/.obj / machine code
    |      kernels, games, apps, HPC
    |      `--emit=asm` for inspection
    |
    +--> LLVM backend --------> optimized native object/binary
    |
    +--> WASM backend --------> wasm module
```

### Reserved Sotlas Vocabulary (Future Contracts)

The following names are intentionally retained as part of the Sotlas language design. They are **reserved future contracts**, not proof that the current compiler supports their complete semantics.

A token, parser branch, syntax-highlighting rule, prototype lowering, website example, or isolated semantic check does **not** make a construct `SUPPORTED`. Every construct below must still pass the project-wide gate:

```text
RFC / semantic contract
  -> grammar
  -> typed AST
  -> semantic rules
  -> negative + positive tests
  -> SIR / lowering
  -> backend
  -> end-to-end
  -> SUPPORTED
```

If older prototype documents assign conflicting meanings to one of these names, the conflict must be resolved by an RFC before the final grammar/ABI is frozen.

#### SRG — Scoped Reference Graph

| Construct | Reserved semantic role |
| :--- | :--- |
| `sole` | Exclusive linear ownership; moving invalidates the source and destruction is deterministic. |
| `co-owned` | Explicit shared ownership with ARC/reference accounting or an equivalent domain-defined mechanism; sharing cost may not be hidden. |
| `island` | Isolated ownership subgraph/region; aliases cannot freely cross its boundary. |
| `whisper` | Non-owning weak/borrowed reference; it never extends lifetime and must obey owner validity. |
| `direct` | Zero-bookkeeping low-level SRG access; it does not itself select a physical address space and carries explicit lifetime/safety obligations. |
| `handover` | Explicit transfer of ownership/resource obligation between bindings, scopes, or domains without intermediate destruction. |
| `quarantine` | Moves a resource into an isolated `island`-style domain and invalidates incompatible external access before reuse/dispatch. |

#### Hardware topology pointers

| Construct | Reserved semantic role |
| :--- | :--- |
| `*rawphys T` | Direct physical/MMIO address with target-appropriate volatility and ordering rules. |
| `*virtmap T` | MMU/page-table mapped virtual address; physical translation must be explicit. |
| `*portwire T` | Processor I/O-port address space, distinct from memory address space. |
| `*dmazone T` | DMA-capable region with explicit alignment, cache/coherency, and CPU/device ownership rules. |
| `*voidzero` | Opaque untyped pointer role analogous to `void*`, but with explicit conversion and topology/safety constraints. |

#### Hardware, critical sections, and interrupts

| Construct | Reserved semantic role |
| :--- | :--- |
| `clinch` | Opens a hardware critical section and creates a compiler-tracked restoration obligation. |
| `revert` | Paired rollback/restoration path for `clinch`; covered exits must restore the protected machine state. |
| `rebound` | Explicit low-level resume/exit after restoration; not a general synonym for `return`. |
| `quench` | Strong memory/persistence ordering barrier with target-specific flush/fence lowering. |
| `gate` | Structured runtime hardware precondition/guard with auditable failure behavior. |
| `trapfn` | Interrupt-handler function with ISR ABI plus effect/stack/return restrictions. |
| `mesh` | Exact-layout aggregate for registers, buses, SoA/ECS, and alignment/offset-sensitive data. |
| `barecore` | Freestanding target profile: no implicit hosted runtime and explicit access to low-level primitives. |
| `probe` | Explicit observability/verification/instrumentation point with declared effects. |
| `pulse` | Deterministic event/signal emission for reactive/flow semantics once delivery rules are formally defined. |

#### Contracts and headerless object model

| Construct | Reserved semantic role |
| :--- | :--- |
| `spec` | Compile-time verifiable API/protocol contract without Sotlas header files. |
| `adopts` | Declares and verifies conformance to one or more `spec` contracts. |
| `mould` | Deterministic compile-time shaping/specialization context for layout or behavior. |
| `moldable` | Explicitly marks an operation as specialization/override-capable; dynamic dispatch must never appear implicitly. |
| `reshape` | Explicit implementation/override of a `moldable` operation with strict signature/contract checking. |
| `capsule` | Visibility restricted to the implementation module/package/capsule. |
| `lineage` | Visibility restricted to a type's inheritance lineage. |
| `irqfree` | Effect contract forbidding operations such as allocation, blocking, and async when they are not interrupt-safe. |
| `discern` | Exhaustive pattern matching over enums/ADTs with compile-time coverage checks. |
| `forge` | Reserved generic/specialization mechanism for compile-time construction and monomorphization; final syntax freezes only in the generics phase. |
| `enclave` | Explicit isolation/trust domain whose entry, exit, capabilities, and resource transfer are checked. |

#### State/memory qualifiers and bit accessors

| Construct | Reserved semantic role |
| :--- | :--- |
| `shielded` | Memory/state protected from concurrency or hardware interference using only the barriers/atomicity required by the target contract. |
| `nvkeep` | State resident in non-volatile storage with explicit durability semantics. |
| `seal` | State mutable only during an authorized initialization window and immutable after sealing. |
| `.slit[lo..hi]` | Extracts a contiguous bit range with width/bounds validation. |
| `.notch[n]` | Extracts/tests one bit with index validation where statically provable. |
| `.strand` | Byte-order/endianness conversion, lowered to a native instruction when available. |
| `.bound[min..max]` | Bounded/refined numeric type with compile-time proof, runtime check, or rejection according to the contract. |

These constructs join the higher-level vocabulary already preserved by the master architecture: `intent`, `flow`, `space`, `state`, `view`, `when`, `guarantee`, `requires`, `ensures`, `proof`, `why`, `explain`, `whatif`, `change`, `transaction`, `compute`, `@target`, `permits`, `effects`, `capabilities`, `@system`, `@interrupt`, `@realtime`, `unsafe`, `shared`, `region`, `device`, `external`, `trusted`, and `isolated`.

Implementation remains dependency-driven: first finish native AST/control-flow/defer/SIR/backend foundations; then formalize ownership; then hardware topology/state/effects/authority; then generics/spec dispatch; then flow/observability; only after those foundations should Intent, Causality, Counterfactuals, Transactions, and heterogeneous-compute semantics be promoted.

## 3. The Universal Systems Spectrum (The 4 Core Pillars)

Sotlas is uniquely architected to replace C, C++, Swift, and C# across four demanding domains without fragmentation:

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           THE UNIVERSAL SPECTRUM                                │
├───────────────────────────────┬─────────────────────────────────────────────────┤
│ 1. Kernel / OS / Baremetal    │ target barecore;                                │
│    (Baremetal, UEFI, Drivers)   │ Zero runtime, zero heap, topology pointers, MMIO│
├───────────────────────────────┼─────────────────────────────────────────────────┤
│ 2. Game Engines & Graphics    │ Value structs, mesh alignment, custom arenas,   │
│    (AAA Renderers, ECS)       │ zero GC latency spikes, SIMD intrinsics         │
├───────────────────────────────┼─────────────────────────────────────────────────┤
│ 3. AI & Tensor Compute        │ Contiguous strided slices, AVX-512 / NEON,      │
│    (Inference, Linear Alg.)   │ zero-copy C/CUDA bridge, memory-mapped models   │
├───────────────────────────────┼─────────────────────────────────────────────────┤
│ 4. Applications & Systems     │ target native;                                  │
│    (Desktop, Mobile, Servers) │ ARC optimization, specs, defer, pattern match   │
└───────────────────────────────┴─────────────────────────────────────────────────┘
```

---

### Pillar 1: Kernel, OS & Baremetal (`target barecore;`)
*Directly challenging C and Zig in systems programming.*

1. **Freestanding Invariant:** Under `target barecore;`, zero libc/libm calls are emitted. There is no implicit dynamic allocator, no thread-local runtime, and no exception unwinding tables.
2. **Memory Topology Pointers:**
   Hardware addresses are not raw integers cast to pointers; they are distinct type-safe topology pointers:
   - `*rawphys T`: Direct physical memory access (page frame tables, APIC MMIO).
   - `*virtmap T`: Linear mapped virtual memory.
   - `*portwire T`: I/O port mapping (emits `in`/`out` instructions on x86).
   - `*dmazone T`: Cache-coherent DMA memory buffers.
3. **Privilege Isolation (`@system` vs `unsafe`):**
   - `unsafe`: Denotes operations that can violate memory safety (pointer arithmetic, type reinterpretation).
   - `@system`: Denotes operations that alter machine state or interact with hardware registers (`cli`, `sti`, writing to control registers `cr0..cr4`, page table reloads).
4. **Deterministic Interrupt Handlers (`trapfn`):**
   Lowers to interrupt calling conventions (`__attribute__((interrupt))` in C/LLVM), automatically saving scratch registers and executing `iretq`.

```sotlas
target barecore;
module kernel::arch::x86_64::paging;

pub struct PageTableEntry {
    raw_bits: u64;

    pub fn new(phys_addr: u64, flags: u64) -> PageTableEntry {
        return PageTableEntry { raw_bits: (phys_addr & 0x000F_FFFF_FFFF_F000) | flags };
    }

    pub fn is_present(self: *const PageTableEntry) -> bool {
        return (self.raw_bits & 0x1) != 0;
    }
}

pub @system fn flush_tlb(vaddr: u64) {
    unsafe {
        emit("invlpg (%0)" : : "r"(vaddr) : "memory");
    }
}
```

---

### Pillar 2: Game Engines & Real-Time Performance
*Directly challenging C++ and Rust in hard real-time graphics and simulation.*

1. **Zero Garbage Collection Guarantee:** Game engines cannot tolerate frame drops caused by GC pauses. Memory is managed deterministically via:
   - Value semantics (`struct`) passed by copy or borrow.
   - Scoped cleanup with `defer`.
   - Engine-provided linear/arena allocators (`FrameArena`, `ScratchPad`).
2. **Data-Oriented Design (DOD) & `mesh`:**
   The `mesh` keyword defines cache-line aligned, tightly packed memory layouts for Structure-of-Arrays (SoA) and Entity Component Systems (ECS):
   ```sotlas
   pub mesh TransformComponent {
       position_x: f32 align(64);
       position_y: f32;
       position_z: f32;
       scale: f32;
   }
   ```
3. **Explicit Destructors (`deinit`):**
   Unlike C++ where destructors can be invoked implicitly in hidden locations, Sotlas structs can define an explicit `deinit(mut self)` that can either be called manually or hooked into `defer`.

---

### Pillar 3: AI, High-Performance Compute (HPC) & Tensor Pipelines
*Directly challenging C++ and Mojo in high-throughput computation.*

1. **Hardware-Accelerated Vector Primitives:**
   First-class SIMD types lowered directly to vector registers (AVX-2, AVX-512, ARM NEON):
   ```sotlas
   pub type Float32x8 = __simd<f32, 8>;
   ```
2. **Contiguous & Strided Tensor Slices:**
   Zero-copy n-dimensional views over contiguous buffers for matrix operations:
   ```sotlas
   pub struct TensorView<T> {
       data: *const T,
       shape: [usize; 4],
       strides: [usize; 4],
   }
   ```
3. **Zero-Overhead C/CUDA FFI:**
   Direct binary interoperability with NVIDIA CUDA Runtime, cuBLAS, and oneDNN. Passing a Sotlas slice to a C function compiles down to passing a raw pointer and length with zero copying or marshalling overhead.

---

### Pillar 4: Applications, Systems Software & Ergonomics
*Directly challenging Swift and C# in application architecture.*

1. **Value Semantics with Automatic ARC Optimization (SIR Level):**
   - High-level reference types (`class`) use Automatic Reference Counting.
   - The SIR SSA compiler performs **Retain/Release Elision**: pairing retains and releases across basic blocks, moving them out of loops, and eliminating redundant reference adjustments entirely.
2. **Exhaustive Pattern Matching & Algebraic Data Types:**
   Enums with payloads (`Result<T, E>`, `Option<T>`) lowered with zero heap boxing.
3. **Clean, Modern Error Propagation (`?`):**
   Replaces clumsy error codes with compile-time checked early exit unwrapping without runtime exception overhead.

```sotlas
target native;
module app::network::client;

import std::net::{TcpStream, SocketAddress};
import std::io::{Result, Error};

pub class HttpClient {
    pub fn fetch(url: &String) -> Result<String, Error> {
        let addr = SocketAddress::parse("127.0.0.1:8080")?;
        let mut stream = TcpStream::connect(addr)?;
        defer stream.close();

        stream.write_all("GET / HTTP/1.1\r\n\r\n".as_bytes())?;
        let response = stream.read_to_string()?;
        return Result::ok(response);
    }
}
```

## 4. Detailed Engineering Blocks (v1.0 Roadmap)

### Block 1 — Language Completeness & Lowering (Critical)

#### 1.1 First-Class Closures with Stack Escape Analysis
* **Grammar:** `|params| -> RetType { ... }` and trailing closures `{ params -> ... }`.
* **Lowering Strategy:**
  - **Non-escaping closures** (passed to `iter.map`, `slice.sort_by`, `lock.with`): Lower to a C function pointer and a raw stack-allocated environment context (`void* ctx`). Zero heap allocation.
  - **Escaping closures** (stored in structs or returned from functions): Wrapped in an ARC-managed closure box (`SotlasClosureBox`) with automatic environment capture.

#### 1.2 Generics — Complete Monomorphization (Surface Syntax TBD)
* **Implementation:**
  - Parse generic definitions into a template AST table.
  - In Sema Pass 2, when a generic type or function is instantiated (`Vec<u32>`, `Vec<String>`), clone the AST with concrete type substitutions.
  - Name mangling format: `_S_M<module>_T<type>_G<args>` (e.g., `_S_foundation_vec_Vec_u32`).
  - Native emitter (`emitter.sotlas`) emits specialized C11 structs and functions for each unique instantiation.
  - SIR pass strips unreferenced monomorphized symbols.

#### 1.3 Specs & Protocols (`spec` and `adopts`)
* **Static Dispatch (Default):**
  When a function accepts `T: adopts Renderable`, the call site is statically monomorphized. Inlining is enabled; call overhead is zero.
* **Dynamic Dispatch (Explicit Object Slices):**
  When dynamic polymorphism is needed, the user specifies `*dyn Renderable`. The compiler synthesizes a fat pointer consisting of:
  - `data: *void`
  - `vtable: *const RenderableVTable` (pointer to statically allocated dispatch table).

#### 1.4 Error Handling (`Result<T, E>` and `?` Operator)
* **Lowering of `expr?`:**
  ```sotlas
  let val = dangerous_op()?;
  ```
  Lowers in SIR SSA to:
  ```sotlas
  let _tmp = dangerous_op();
  if _tmp.is_err() {
      return Result::err(_tmp.unwrap_err());
  }
  let val = _tmp.unwrap();
  ```
  Zero stack unwinding, zero exception overhead, 100% deterministic ABI.

#### 1.5 `defer` Statement
* **Semantics:** Executes at block exit in Last-In, First-Out (LIFO) order.
* **Lowering Strategy:**
  - The AST records deferred statements per lexical block.
  - On any exit path from the block (`return`, `break`, `continue`, or normal scope close), the compiler automatically injects the deferred statements in reverse registration order before emitting the jump.

#### 1.6 Industrial Owned `String` & `StringSlice`
* **Architecture:**
  - `StringSlice` (`&str`): Fat pointer `(ptr: *const u8, len: usize)`. Read-only, borrowed, zero allocation. Valid for string literals and substrings.
  - `String`: Owned, growable UTF-8 string `(ptr: *mut u8, len: usize, cap: usize, allocator: *Allocator)`.
  - Methods: `concat`, `slice`, `find`, `starts_with`, `trim`, `split`, `to_uppercase`, `format`.

#### 1.7 Universal Iterator Protocol
* **Spec Definition:**
  ```sotlas
  pub spec Iterator<T> {
      fn next(mut self: &mut Self) -> Option<T>;
  }
  ```
* **Lowering of `for item in collection`:**
  ```sotlas
  let mut _iter = collection.iter();
  while let Option::some(item) = _iter.next() {
      // loop body
  }
  ```

### Block 2 — Compiler Architecture & Toolchain Polish

#### 2.1 Clean Compiler Diagnostics (Eliminating Raw Clang Leaks)
* **Problem:** When `sotlas_native.exe` produces invalid C or encounters linker errors, it dumps raw Clang/MSVC diagnostics referencing generated temporary C files.
* **Remedy:**
  - The frontend and Sema must catch 100% of semantic and type errors *before* codegen.
  - When backend compilation fails, the compiler traps the error line number, maps it through the internal source map, and renders a clean, Rust-style diagnostic showing the user's actual `.sotlas` code with line/column caret pointers.

#### 2.2 Precise Source Maps (`#line` Directives & DWARF)
* In C11 codegen, emit `#line <num> "<source_file>.sotlas"` before every statement.
* When debugging binaries compiled through Clang/GCC/MSVC using GDB, LLDB, or Visual Studio, the debugger steps directly through `.sotlas` source files rather than generated C files.

#### 2.3 Incremental Compilation & Build Caching
* Hash input `.sotlas` source files and module dependencies using BLAKE3/SHA-256.
* Cache compiled `.o` / `.obj` artifacts in `.sotlas-cache/`.
* If neither the file nor its imported modules have changed, link the cached object directly, reducing incremental build times to sub-50 milliseconds.

#### 2.4 Multi-Target Cross-Compilation
* Standardize on target triples:
  - `x86_64-unknown-none-elf` (Baremetal / Baremetal)
  - `x86_64-pc-windows-msvc` (Windows Native)
  - `x86_64-unknown-linux-gnu` (Linux Native)
  - `aarch64-unknown-linux-gnu` (ARM64 Server)
  - `aarch64-apple-darwin` (macOS Apple Silicon)
  - `wasm32-unknown-wasi` (WebAssembly Systems)
* Explicit driver flags: `sotlas build --target x86_64-unknown-none-elf`.

#### 2.5 Unified CLI (`sotlas run`, `sotlas test`, `sotlas check`)
* `sotlas build <file>`: Compiles binary/library.
* `sotlas run <file> [-- args]`: Compiles to memory or temporary cache and executes immediately.
* `sotlas check <file>`: Runs lexer, parser, sema, and SIR passes without codegen for instant feedback in editors (<20ms).
* `sotlas test`: Discovers and executes all unit tests defined in `@test fn` blocks.

### Block 3 — Standard Library Tier-1 Architecture

The standard library is structured into three strictly isolated layers:

```
┌─────────────────────────────────────────────────────────────┐
│                    stdlib/foundation/                       │
│    Hosted APIs: FileSystem, Sockets, Threads, Process, JSON │
├─────────────────────────────────────────────────────────────┤
│                       stdlib/core/                          │
│    Freestanding APIs: Option, Result, Slices, Math, Mem     │
├─────────────────────────────────────────────────────────────┤
│                      stdlib/system/                         │
│    Hardware Intrinsics, MMIO, CPU Registers, Page Tables    │
└─────────────────────────────────────────────────────────────┘
```

1. **`core::math`:** Zero-libm pure implementations: `sin`, `cos`, `sqrt`, `pow`, `abs`, `min`, `max`, `clamp`, `floor`, `ceil`. Fast polynomial approximations for freestanding environments.
2. **`core::fmt`:** High-performance display protocol:
   ```sotlas
   pub spec Display {
       fn fmt(self: &Self, writer: &mut Formatter) -> Result<(), Error>;
   }
   ```
3. **`foundation::hashmap`:** Swiss-Table style Robin Hood hashing with SIMD group probing for cache-friendly lookups.
4. **`system::thread` & `sync`:** Cross-platform threading primitives: `Thread`, `Mutex`, `RwLock`, `CondVar`, `Atomic<T>`, and `Channel<T>`.
5. **`system::time`:** High-resolution timing: `Instant`, `Duration`, `SystemTime`, `MonotonicClock`.

> [!IMPORTANT]
> To establish Sotlas as a respected, tier-1 systems project, all signatures of automated generation, inconsistent dialects, and patronizing comments must be systematically eradicated.

#### 5.1 Elimination of Auto-Generated Artifacts
* **Current Violation:** Headers like `/* Gerado automaticamente pelo compilador Sotlas Bootstrap v0.1.0 */` and `/* NÃO EDITE */`.
* **Fix:** Replace with standard, professional systems headers:
  ```c
  /* Sotlas Compiler - C11 Code Generator Output */
  /* Target: x86_64-pc-windows-msvc */
  ```
  Or omit commentary altogether and begin directly with file declarations.

#### 5.2 Standardization on Professional Systems Comments
* **Rule:** Source code comments must explain *rationale*, *invariants*, and *hardware quirks*, not syntax basics.
* **Bad (Tutorial/AI Style):**
  ```sotlas
  // Here we loop through all elements in the array
  // and we check if the element is equal to target
  ```
* **Good (Professional Systems Style):**
  ```sotlas
  // Invariant: buffer must be 64-byte aligned to satisfy AVX-512 load instructions.
  // We process 16 elements per iteration; scalar loop handles the remainder.
  ```
